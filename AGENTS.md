# Конвенції репозиторію

## Закінчив зміну — закомітив і запушив

**Кожна завершена зміна = `make check` + один коміт + пуш у `main`.** Не «в кінці
сесії», не «коли назбирається»: незапушена робота існує лише на одній машині.
У повідомленні пояснювати **чому**, а не перелічувати файли — diff і так їх показує.

## Журнал і CHANGELOG не читаються — тільки дописуються

Ні `cat`, ні `tail`, ні Read. Щоб дописати в кінець, попередні записи знати не
треба, а прочитаний журнал — це десятки кілобайт чужих рішень у контексті замість
коду, який зараз правиться. Формати нижче фіксовані саме тому: вони не залежать
від того, що вже у файлі. Виняток — користувач прямо просить щось у них знайти.

Журнал — після кожного змістовного кроку. Не «створив файл», а те, чого не видно
з diff: чому саме так, що перевірено, що свідомо відкладено.

```bash
cat >> docs/worklog/$(date +%F).md <<'EOF'

## HH:MM — <що робив>
**Задача:** <фаза + крок>
**Змінено:** <шляхи до файлів>
**Рішення:** <що вирішено і чому; лише якщо був вибір>
**Перевірено:** <команда → результат; без цього крок не зроблений>
**Відкрито:** <що лишилось незробленим>
EOF
```

CHANGELOG — раз на сесію, і лише те, що помітить користувач: «пост більше не
дублюється в каналі», а не «додано колонку `tg_extra_message_ids`».

```bash
cat >> CHANGELOG.md <<'EOF'

## <YYYY-MM-DD> — <що змінилось для користувача, одним рядком>

- **<Можливість чи виправлення>.** <Наслідок і причина.>
EOF
```

`docs/state.md` — навпаки, **перезаписується**: це не історія, а відповідь на
питання «в якому стані все зараз». Оновлювати, коли змінилось те, що там
написано: нова можливість, знайдений чи закритий дефект, змінене обмеження.

## Документація — разом зі змінами, а не «потім»

| Що змінилось | Що оновити |
| --- | --- |
| Структура, потоки даних, схема БД | `docs/architecture.md` |
| Архітектурне рішення | новий `docs/adr/NNNN-*.md` |
| Деплой, env, експлуатація | `docs/runbook.md` |
| HTTP-контракти | `docs/api.md` |
| Дефолтні промпти чи змінні | `docs/prompts.md` |

## Код

- Спільні типи й zod-схеми — у `packages/shared`, а не дублювати між server і web.
- Доменні енуми оголошені один раз у `packages/shared/src/enums.ts`; Drizzle
  `pgEnum` і zod будуються з тих самих масивів.
- Валідація вхідних даних — zod на межі HTTP, не всередині бізнес-логіки.
- Увесь доступ до `process.env` — тільки через `apps/server/src/config.ts`.
- Логи структуровані (`pino`), з полями `project_id` / `post_id` / `job_id`.
- Секрети ніколи не повертаються клієнту — тільки маска через `maskStoredSecret`.
- Мова інтерфейсу та повідомлень про помилки — українська.

## Чого не робити

- Не зберігати опубліковані тексти й зображення: лишається лише `permalink`
  (`docs/adr/0002-telegram-as-content-store.md`).
- Не хардкодити ID моделей — брати з каталогу провайдера.
- Не покладатись на промпт там, де правило форсується кодом (санітизація SVG).
- Не додавати Redis чи зовнішній брокер: черга живе в Postgres.
- Не писати міграції руками — тільки `make migration`. Рукописний SQL без
  свіжого знімка ламає наступний `generate`. Якщо все ж довелось: згенерувати
  наступну міграцію, лишити її знімок, підмінити SQL.
- **Не читати `node_modules`** — ні пошуком, ні обходом дерева. Пошук по коду
  обмежувати `apps/`, `packages/`, `docs/`; потрібен API залежності — дивитись
  її `.d.ts` за точним шляхом.

## Команди

```bash
make check      # типи, тести, секрети в індексі — перед кожним комітом
make up         # check + збірка + міграції + контейнери (api :3000, web :5173)
make down       # зупинити
make logs       # логи app
make migration  # згенерувати міграцію після зміни schema.ts
npm run dev     # найшвидший цикл: без докера, з Vite HMR
```
