# AGENTS.md — конвенції репозиторію

Читається агентом на початку кожної сесії. Тримати коротким.

`CLAUDE.md` — символьне посилання на цей файл, а не окремий документ: Claude Code
інжектить у контекст саме `CLAUDE.md`, тож посилання робить ці правила
прочитаними завжди, а не лише коли агент здогадається піти за вказівником.
Копія замість посилання розійшлася б із оригіналом при першій же правці.

## Обовʼязкове правило: закінчив зміну — закомітив і запушив

**Кожна завершена зміна = один коміт + пуш у `main`.** Не «в кінці сесії», не
«коли назбирається»: незапушена робота існує лише на одній машині, і будь-хто,
хто подивиться в репозиторій, побачить застарілу картину.

Репозиторій: `git@github.com:kexxx777xxx/telegram-content-factory.git`
(SSH — HTTPS-пуш не налаштований, `gh` не встановлено).

Перед комітом:

1. `npm run typecheck` — має бути чисто.
2. `npm test` — має бути чисто.
3. Перевірити, що не потрапили секрети: `app.env`, ключі, токени, бекапи БД.
4. Оновити `CHANGELOG.md`, `docs/worklog/` і `docs/state.md` (див. нижче).

У повідомленні коміта пояснювати **чому**, а не перелічувати файли — diff і так
їх показує.

## Обовʼязкове правило: історія змін

Три різні записи, і кожен відповідає на своє питання. Жоден не заміняє інший.

| Файл | Питання | Горизонт |
| --- | --- | --- |
| `docs/worklog/YYYY-MM-DD.md` | що робив саме зараз і чому саме так | один крок |
| `CHANGELOG.md` | що змінилось для того, хто користується системою | реліз |
| `docs/state.md` | як система влаштована **зараз** | поточний момент |

### `docs/worklog/` — журнал дій

**Після кожного змістовного кроку дописати запис.** Файл на день, лише дозапис —
ніколи не перезаписувати попередні записи.

```markdown
## HH:MM — <що робив>
**Задача:** <фаза + крок>
**Змінено:** <шляхи до файлів>
**Рішення:** <що вирішено і чому; лише якщо був вибір>
**Перевірено:** <команда → результат; без цього крок не вважається зробленим>
**Відкрито:** <що лишилось незробленим>
```

Не описувати очевидне («створив файл»). Записувати те, чого не видно з diff:
причину вибору, що саме перевірено, що свідомо відкладено.

### `CHANGELOG.md`

Формат [Keep a Changelog](https://keepachangelog.com/uk/1.1.0/). Пише про
**наслідок для користувача**, а не про рефакторинг: «пост більше не дублюється в
каналі», а не «додано колонку `tg_extra_message_ids`». Причина — одним рядком:
без неї запис через півроку нічого не пояснює.

### `docs/state.md` — актуальний стан

Знімок системи на сьогодні: що працює, що ні, які знані обмеження, що
неперевірене. **Перезаписується**, а не дописується — це не історія, а відповідь
на питання «в якому стані все зараз». Оновлювати, коли змінилось те, що там
написано: нова можливість, закритий чи знайдений дефект, змінене обмеження.

## Код

- TypeScript strict, ESM, `.js`-розширення в імпортах (NodeNext).
- Спільні типи й zod-схеми — у `packages/shared`, а не дублювати між server і web.
- Доменні енуми оголошені один раз у `packages/shared/src/enums.ts`; Drizzle
  `pgEnum` і zod будуються з тих самих масивів.
- Валідація вхідних даних — zod на межі HTTP, не всередині бізнес-логіки.
- Увесь доступ до `process.env` — тільки через `apps/server/src/config.ts`.
- Логи структуровані (`pino`), з полями `project_id` / `post_id` / `job_id`.
- Секрети ніколи не повертаються клієнту — тільки маска через `maskStoredSecret`.
- Мова інтерфейсу та повідомлень про помилки — українська.

## Чого не робити

- Не зберігати опубліковані тексти й зображення: після публікації лишається
  лише `permalink`. Див. `docs/adr/0002-telegram-as-content-store.md`.
- Не хардкодити ID моделей — брати з каталогу провайдера.
- Не покладатись на промпт там, де правило можна форсувати кодом
  (санітизація SVG — приклад).
- Не додавати Redis чи зовнішній брокер: черга живе в Postgres.
- **Не читати `node_modules`** — ні рекурсивним пошуком, ні обходом дерева.
  Пошук по коду завжди обмежувати `apps/`, `packages/`, `docs/`. Потрібен API
  залежності — дивитись її `.d.ts` за точним шляхом, а не сканувати теку.

## Команди

### Міграції

`npm run db:generate` порівнює `schema.ts` з **останнім знімком** у
`migrations/meta/`. Тому міграцію, написану руками, не можна лишати без знімка:
drizzle-kit і далі бачитиме стан на момент останнього знімка, наступний
`generate` спробує повторити вже застосовані зміни, а на питаннях про
перейменування впаде без TTY.

Якщо міграцію все ж довелось написати руками — згенерувати наступну звичайним
`db:generate`, лишити її **знімок** (він відображає справжній поточний стан) і
замінити її SQL на потрібний, прибравши повтор уже застосованого.

```bash
docker compose up -d db     # тільки база, для локальної розробки
npm run db:migrate          # застосувати міграції
npm run dev                 # server (:3000) + web (:5173)
npm run typecheck           # усі воркспейси
npm test                    # vitest
npm run db:generate         # згенерувати міграцію після зміни schema.ts
```
