## 18:57 — проста ієрархія ключів замість областей
**Задача:** переробка моделі API-ключів на вимогу «є ключі в налаштуваннях, один дефолтний;
у проєкті можна вибрати один, і на кожну дію свій».
**Змінено:** `packages/shared/src/{enums,schemas}.ts`, `apps/server/src/db/schema.ts`,
міграції `0004`/`0005`, `apps/server/src/ai/{keys,chain,chains}.ts`,
`apps/server/src/media/pipeline.ts`, `apps/server/src/services/{apiKeys,generationConfig,projects}.ts`,
`apps/server/src/api/routes/{keys,generation}.ts`,
`apps/web/src/{pages/SettingsPage,components/GenerationConfig,components/ProjectForm,api/client}.tsx|ts`,
`apps/server/test/{db,load}.test.ts`, `docs/{architecture,api}.md`, `CHANGELOG.md`.

**Рішення:**
- `scope`, `key_preference` і прикріплення ключа до **кроку** прибрані. Ключ живе на трьох
  рівнях: `model_chains.api_key_id` (дія) → `projects.api_key_id` (проєкт) → `api_keys.is_default`.
  Одне питання «за що платить ключ» замість двох («звідки ключ» + «який саме»).
- `resolveKey()` повертає **один** ключ, а не список. Перебору між ключами немає навмисно:
  інакше «зображення оплачує платний ключ» деградує до побажання. Альтернатива — наступна
  **модель** ланцюжка, і про це сказано користувачу до початку роботи.
- Ключ дії зберігається на рядку ланцюжка, тож закріплення працює і глобально, і в межах
  проєкту. Побічний наслідок: щоб закріпити ключ у проєкті, який ланцюжок успадковував,
  `setChainKey` спершу матеріалізує успадкований ланцюжок — інакше ключ не було б де зберегти.
- Позначення ключа дефолтним **знімає** позначку з попереднього замість помилки на унікальному
  індексі: це вказівка, а не конфлікт.
- Видалення дефолтного ключа передає роль найстарішому з решти. `on delete set null` рятує
  посилання з проєктів і ланцюжків, але без дефолтного ключа не працювало б узагалі нічого.

**Перевірено:**
- `npm run typecheck` → чисто; `npm test` → 55 тестів (4 нові на ієрархію: дефолт, проєкт,
  дія перекриває проєкт, вимкнений ключ пропускається); `npm run build` → чисто.
- `npm run db:migrate` на робочій базі; в БД `is_default` проставлено, колонки `scope`,
  `project_id`, `key_preference` зникли.
- Живий API: пін платного ключа на `image` → у проєкті `keyLevel=action`; ключ проєкту →
  всі інші дії `project`, `image` лишається `action`; зняття обох → всюди `default`.
- Живий dry-run `post_text` → успіх з першого кроку, `attempts[0].keyLevel = default`.
- `PATCH /projects/:id` з одним полем не скинув `persona`/`postsBuffer` (регресія фази 1).

**Втрачений час і його причина:** призначення дефолтного ключа в міграції `0005` мовчки не
відпрацювало — стейтмент починався з рядка коментаря `--`, і drizzle його пропустив. Обидва
дата-стейтменти переписані так, щоб починатися з SQL. Урок загальний: у міграціях коментар
ставити **після** першого ключового слова, бо пропуск нічим не сигналізується.

**Відкрито:** гілка image-моделі досі не перевірена живим викликом (потрібен платний ключ і
реальна генерація); `sendPhoto` у канал теж не перевірено.

## 19:25 — кнопка «Опублікувати зараз»
**Задача:** ручний запуск публікації як готового, так і ще не згенерованого поста.
**Змінено:** `apps/server/src/services/publishNow.ts` (новий),
`apps/server/src/api/routes/{posts,projects}.ts`,
`apps/web/src/components/PostsCard.tsx`, `apps/web/src/api/client.ts`,
`apps/server/test/db.test.ts`, `docs/api.md`, `CHANGELOG.md`.

**Рішення:**
- Один шлях на два випадки: готовий пост → `publish_post`, будь-який незавершений →
  `generate_and_publish`. Це та сама джоба, якою працює режим без буфера, тож ручний запуск не
  вводить окремої гілки, яку довелось би окремо лагодити.
- Ручний запуск видаляє джобу `generate_post` цього поста у статусі `pending`. Без цього дві
  джоби генерували б наперегони: одна ставить пост у `generating`, друга бачить його
  недоробленим і падає на публікації. Джобу `running` не чіпаю — там дедуп-ключ.
- `skipped` повертається в `planned`: для планувальника це кінцевий стан, але рішення людини
  його скасовує, а генерація зі `skipped` не стартує.
- Проєктна кнопка створює слот, якщо жодного немає. Інакше в проєкті з `postsBuffer = 0` кнопка
  мертва саме тоді, коли потрібна.
- Готовий пост має пріоритет над раніше запланованим при виборі «найближчого»: публікувати вже
  оплачене дешевше, ніж генерувати нове. Сортування виписане в SQL, бо `order by status`
  впорядкувало б за порядком оголошення енуму, де `planned` іде перед `ready`.
- Підтвердження в діалозі: на відміну від решти дій картки, цю не відкотити.

**Перевірено:**
- `npm run typecheck`, `npm run build` — чисто; `npm test` → 61 тест (6 нових на запуск:
  готовий, незгенерований, зняття джоби `pending`, відмова для `published`/`generating`,
  пріоритет готового, створення слоту).
- Живий API: `409` для опублікованого («Пост уже опубліковано») і для `generating`, `404` для
  неіснуючого. Реальну публікацію в канал **не запускав** — це вихід у бойовий канал, і робити
  це без прямої вказівки не можна.
- В UI обидві кнопки рендеряться: проєктна в шапці картки постів, у розкритому рядку —
  «Згенерувати і опублікувати» для поста без тексту.

**Втрачений час і його причина:** близько двадцяти хвилин ганявся за «флакі» тестами в
`queue claiming`. Причина була в моїх же діагностичних прогонах: паралельний процес vitest
клеймив джоби з тієї самої тестової бази, і `claimJob` у тесті повертав `null`. Після зупинки
зайвих процесів — 11 чистих прогонів поспіль. Урок: тестова база спільна, тож два прогони
одночасно завжди даватимуть саме такі симптоми.

**Відкрито:** кнопка не перевірена наскрізним живим прогоном (публікація в канал) — потрібне
ваше рішення, на якому пості це робити.
