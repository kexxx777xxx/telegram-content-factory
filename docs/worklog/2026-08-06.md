тести, `docs/{api,architecture,runbook}.md`, `CHANGELOG.md`, `CLAUDE.md`.

**Рішення:**
- Перемикачі логу — **на проєкт** (вибір користувача), окремою таблицею `post_logs`, а не в
  `events`: тут громіздкий текст, який вмикають свідомо і який чиститься за власним строком.
- Помилки моделі пишуться, якщо ввімкнено **будь-який** із двох перемикачів: падіння — саме той
  випадок, заради якого лог заводять, і ховати його за перемикачем «відповіді» безглуздо.
- Зображення не логуються — лише рядок про модель і розмір. Інакше це той самий локальний архів
  картинок, який прибрав ADR 0002.
- `writeLog` ніколи не кидає: щоденник не має права завалити роботу, про яку він веде записи.
- Перемикачі кешуються на 30 с (виклик на кожен крок ланцюжка), а збереження проєкту скидає кеш.
- Пости й теми зведені в одну вкладку «Контент». Вони й справді виглядали дублюванням, бо обидва
  відповідають на «що канал скаже». Різниця в тому, що слот має дедлайн, а тема — ні; тож слоти
  зверху, банк під ними як постачання.
- Іконку стану БД прибрано: постійний індикатор нормального стану щодня забирає увагу, щоб нічого
  не сказати, і до моменту, коли він щось означає, око вже навчилось його пропускати.
- Слоти сортуються **при збереженні**, а не під час набору: інакше поле виїжджає з-під курсора.

**Знайдено дорогою (обидва — справжні дефекти):**
1. **Сервер упав повністю.** Модель віддала SVG з `feTurbulence` + `feDisplacementMap`; resvg
   зробив assert у Rust, а паніка в нативному аддоні вбиває процес Node разом із чергою й
   планувальником. Санітайзер тепер вирізає всі фільтри — для пласкої схеми вони нічого не дають.
   Тест відтворює саме цей payload.
2. **Пост назавжди застрягав у `generating`** після такого падіння: генерація не стартує з цього
   статусу, тож джоба вічно звітувала «skipped». Publisher tick повертає такі пости в `planned`
   через 20 хвилин.

**Перевірено:**
- `npm run typecheck`, `npm run build` — чисто; `npm test` → 64 тести (3 нові: перемикачі логу,
  ретеншн за строком проєкту, вирізання фільтрів із SVG).
- Живий прогін: увімкнув лог у проєкті, витягнув джобу генерації наперед → у логу чотири записи
  (`request`/`response` для `post_text` і `svg`) з токенами, часом і ключем. Саме там і видно
  той SVG з фільтрами, що поклав сервер.
- UI у браузері: вкладки перемикаються, рядок поста тримає лише статус/час/тему/лінк, спойлери
  «Як це згенеровано» і «Лог запитів до моделей» відкриваються, лог вантажиться при відкритті.
- Публікацію в канал не запускав.

**Відкрито:**
- `publish_post` цього проєкту падає з `Bad Request: chat not found` — канал `-1003651366307`
  недоступний боту. Це конфігурація каналу, не код.
- Ізоляція рендерера від паніки (окремий процес) не робилась: вирізання фільтрів закриває відомий
  клас, але будь-який інший assert у resvg так само вбʼє процес.

## 13:55 — журнал, вкладки, фільтри і batch-тариф
**Задача:** другий пакет зауважень до UI + єдиний журнал + підтримка Gemini Batch API.
**Змінено:** `packages/shared/src/{enums,schemas}.ts`, `apps/server/src/db/schema.ts`,
міграції `0007`–`0009`, `apps/server/src/services/activityLog.ts` (замість `postLog.ts`),
`apps/server/src/ai/{batch,gemini,provider,chain,keys}.ts`,
`apps/server/src/services/{posts,topics,publish,projects,apiKeys}.ts`,
`apps/server/src/queue/{handlers,enqueue,prune}.ts`, `apps/server/src/scheduler/index.ts`,
`apps/server/src/api/routes/{posts,projects,topics}.ts`,
`apps/web/src/components/{ProjectForm,PostsCard,TopicBank,ProjectJournal}.tsx`,
`apps/web/src/pages/{ProjectPage,SettingsPage}.tsx`, тести, docs, CHANGELOG.

**Рішення:**
- **Один журнал замість двох логів.** Окремі перемикачі «запити» і «відповіді» завжди вмикали
  разом; промпт без відповіді нічого не пояснює. Одна таблиця `logs` на все, бо питання
  «чому цей пост такий» читається хронологічно, а два півжурнали довелось би зшивати очима.
- У журналі тепер і те, чого раніше не було: звідки тема (авто/вручну), коли поповнювався банк,
  кожен крок генерації, публікація з поміткою авто/вручну.
- **Теми зведені під пости.** Вони й виглядали дублюванням, бо обидва відповідають на «що канал
  скаже». Але слот має дедлайн, а тема ні — тож банк став згорнутим блоком під списком слотів.
- Лічильники статусів зробив кнопками фільтра: вони й так були першим, на що дивишся, а окремий
  контрол повторював би ті самі слова.
- **Batch — тільки для того, що може чекати.** Планове поповнення тем (поріг там *мінімум*, тож
  банк не порожніє) і текст поста, коли до слоту більше за SLA вендора з запасом. Тема під
  конкретний пост і ручна кнопка лишились синхронними: це критичний шлях.
- Кожне замовлення несе власний дедлайн, після якого джоба скасовується у вендора. Без цього
  «дешевше» тихо стає «слот не вийшов вчасно».
- У batch іде лише **перший крок** ланцюжка: фолбек існує для «модель недоступна зараз», а
  замовлення, яке читатимуть через добу, такого моменту не має.
- Пост чекає на batch зі статусом `planned`, а не `generating`: «генерується» означає, що модель
  працює просто зараз, і reaper застряглих генерацій не має чого підбирати.
- **Лог у Telegram не робив** — на пряме питання відповів: TG не має ні пошуку, ні звʼязку з
  постом, ріже по 4096 символів і лімітує ~20 повідомлень/хв на чат. Обрано БД зі строком.

**Знайдено дорогою (справжній дефект):** `enqueue` ставив `run_after` за годинником застосунку, а
`claimJob` порівнює з `now()` бази. Контейнер відстає від хоста на 88 мс (після сну VM — на
секунди), тож кожна джоба була невидимою рівно на цю різницю. Двічі списував це на паралельні
прогони тестів — насправді це був продуктовий баг, який у проді дав би тихі затримки публікацій.
Час тепер ставить сама база.

**Перевірено:**
- `npm run typecheck`, `npm run build` — чисто; `npm test` → 69 тестів (нові: годинник черги,
  дедлайн batch, відмова batch на ключі без прапорця, походження теми в журналі).
- П'ять прогонів `load + db` поспіль без падінь — та сама пара, що «флакала» два дні.
- **Живий batch:** відправка через платний ключ → `batches/4efjd3jwi8cvac3lht89…`, відповідь за
  ~90 секунд, джоба черги припаркована без витрати спроб, потім 5 тем у банку і повний слід у
  журналі («Відправлено в batch», «Batch завершився», «Банк тем поповнено», 5× «Тема згенерована»).
- Витяг тексту з batch-відповіді довелось лагодити: `response.text` — це геттер класу SDK, а
  всередині batch приходить звичайний обʼєкт, тож текст збирається з `parts`.

**Відкрито:**
- Текст поста через batch живим прогоном не перевірявся — потрібен слот далі ніж за 26 годин.
- `image`/`svg` через batch не пускаю: вони залежать від тексту поста, тож ланцюжок розтягнувся б
  на дві доби. Механізм для цього готовий, вмикати — окреме рішення.
