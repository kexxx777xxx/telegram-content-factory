# ADR 0001 — PostgreSQL замість JSON-файлу

- **Дата:** 2026-08-02
- **Статус:** прийнято

## Контекст

Вихідний PRD передбачав файлове сховище: `/data/db.json` + `db_backup.json`, з синхронізацією
частини стану в `.env`. Для одного каналу це працює.

Продукт розширено до мультипроєктності: десятки каналів, у кожного свій банк тем, свій розклад і
свої пости. З цим зʼявляються паралельні писачі — планувальник, пул воркерів, publisher і HTTP-шар
змінюють стан одночасно.

## Проблема

JSON-документ оновлюється лише цілком. Це дає:

- перезапис усього файлу на кожну дрібну зміну (лічильник спроб, статус джоби);
- відсутність транзакцій: «взяти джобу і позначити зайнятою» не атомарне;
- гонки між планувальником і воркерами, які губляться мовчки;
- ризик втрати всього стану при падінні під час запису;
- відсутність часткових індексів, на яких тримається ідемпотентність черги.

## Рішення

PostgreSQL 16 як єдине сховище стану. Drizzle ORM + drizzle-kit для схеми й міграцій.

JSON лишається, але в іншій ролі: щоденний `pg_dump | gzip` в адмін-чат Telegram як **бекап і
експорт**, а не як робоче сховище.

## Наслідки

**Позитивні**

- `SELECT … FOR UPDATE SKIP LOCKED` дає чергу без окремого брокера ([ADR 0005](0005-postgres-queue-no-redis.md)).
- Часткові унікальні індекси дають ідемпотентність постановки джоб і захист від подвійного
  бронювання слоту.
- `pg_advisory_lock` захищає лідерство планувальника.

**Ціна**

- Ще один контейнер в експлуатації; треба бекапити том.
- Зміна схеми тепер вимагає міграції, а не редагування структури «на льоту».

## Альтернативи

- **SQLite** — знімає окремий контейнер, але при кількох воркерах упирається в блокування
  на запис і не має `SKIP LOCKED`.
- **Лишити JSON із файловим локом** — власна реалізація того, що БД уже робить, з гіршими
  гарантіями.
