# ADR 0003 — Ліміт і circuit breaker рахуються на ключ

- **Дата:** 2026-08-02
- **Статус:** прийнято

## Контекст

Конфігурація ключів: **один ключ на проєкт + один глобальний фолбек**. При десятках проєктів
питання «хто саме вичерпав квоту» стає центральним для планування навантаження.

Спокуса — згрупувати ключі в «групи квоти» (`quota_group`) і рахувати ліміт на групу, бо квота
Gemini API насправді прив'язана до Google Cloud проєкту, а не до окремого ключа. Тоді 429 на
одному ключі одразу вимикав би всі ключі того ж акаунту й економив марні запити.

## Проблема з групуванням

Визначити, чи два ключі належать одному акаунту, **неможливо ззовні**. API не повертає
приналежність, а покладатись на те, що користувач правильно розставить групи вручну, — значить
покласти коректність тротлінгу на ручний конфіг. Помилка в такому конфігу дає хибне блокування:
робочий ключ вимикається через чужий 429, і канал мовчки пропускає слоти.

## Рішення

Стан ліміту — рядок `rate_limit_state` з первинним ключем `(api_key_id, model)`. Жодних груп,
жодних здогадок.

- Token bucket рахується на пару `(ключ, модель)`.
- 429 з `retryDelay` пише `blocked_until` рівно для цієї пари.
- Інші ключі не зачіпаються ніколи.

## Наслідки

**Позитивні**

- Неможливе хибне блокування робочого ключа.
- Поведінка передбачувана і пояснювана: кожен рядок стану має очевидне джерело.
- Конфігурація лишається простою — користувач додає ключ, і все.

**Ціна**

Якщо два ключі справді ділять квоту, другий дізнається про це власним 429.

Точніше: зайвих запитів не один, а **до `WORKER_CONCURRENCY`** — кілька воркерів встигають пройти
`acquire()` до того, як перший 429 запишеться в `blocked_until`. Це підтверджено навантажувальним
тестом: при пулі з 4 воркерів і 30 джобах вичерпаної моделі торкнулись 2 запити замість 30.

Ціна лишається прийнятною: кілька запитів проти тихого простою каналу. Але формулювання «один
зайвий запит» було б неправдою.

## Наслідок для глобального ключа

Глобальний фолбек — спільний ресурс усіх проєктів, тож він вичерпується найшвидше. Йому
призначається найжорсткіший bucket і окремий `daily_request_budget`, інакше перший же сплеск
з'їдає його для всіх одразу.
