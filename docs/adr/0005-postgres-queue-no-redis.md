# ADR 0005 — Черга живе в Postgres, без Redis

- **Дата:** 2026-08-02
- **Статус:** прийнято

## Контекст

Потрібна черга задач із затримкою запуску (`run_after`), пріоритетами, ретраями з backoff,
ідемпотентною постановкою і кількома конкурентними воркерами.

## Рішення

Таблиця `jobs` у тому ж Postgres. Claim через:

```sql
select … from jobs
 where status = 'pending' and run_after <= now()
 order by priority desc, run_after
 for update skip locked
 limit 1
```

Ідемпотентність — партіальний унікальний індекс:

```sql
create unique index jobs_dedupe_uniq on jobs (dedupe_key)
  where status in ('pending','running') and dedupe_key is not null;
```

Той самий `dedupe_key` не можна поставити двічі, поки джоба активна, але **можна** перевикористати
після завершення — саме те, що треба для повторюваних слотів.

Лідерство планувальника — `pg_advisory_lock`.

## Наслідки

**Позитивні**

- Постановка джоби і зміна стану домену — в **одній транзакції**. З окремим брокером це
  розподілена транзакція або втрачені джоби.
- Нема другого сховища, яке треба піднімати, моніторити й бекапити.
- Черга видима звичайним SQL: інциденти розбираються `psql`, без спеціального інструменту.
- Ретраї, `run_after` і пріоритети — це просто колонки.

**Ціна**

- Пропускна здатність нижча, ніж у спеціалізованого брокера. Для цього навантаження
  (десятки проєктів × одиниці постів на день ≈ сотні джоб на добу) запас на порядки.
- Опитування замість push. Тік раз на секунду з партіальним індексом `jobs_claim_idx` коштує
  дешево; `LISTEN/NOTIFY` можна додати пізніше, якщо знадобиться.

## Коли переглянути

Якщо навантаження виросте до тисяч джоб на хвилину або знадобиться кілька інстансів воркерів на
різних машинах — тоді має сенс дивитись на окремий брокер. До того це передчасна складність.
