# ADR 0006 — npm workspaces і файл `app.env`

- **Дата:** 2026-08-02
- **Статус:** прийнято

Два дрібні, але наочні відхилення від початкового плану. Обидва зроблені після зіткнення з
реальністю, а не за вподобанням.

## 1. npm workspaces замість pnpm

**Контекст.** План передбачав pnpm workspaces. На машині відсутні і `pnpm`, і `corepack`
(Node 26 більше не постачає corepack у комплекті).

**Рішення.** npm workspaces (npm 11). Структура монорепо ідентична: `apps/*`, `packages/*`,
внутрішні залежності через `"@tcf/shared": "*"`.

**Чому не поставити pnpm.** Це означало б глобальне встановлення в систему користувача заради
переваги, якої тут не видно: три пакети, і виграш pnpm у дедуплікації сховища нерелевантний.

**Наслідок.** `node_modules` більший, ніж був би з pnpm. На функціональність не впливає.

## 2. Конфіг у `app.env`, а не в `.env`

**Контекст.** Docker Compose автоматично підхоплює `./.env` для власної підстановки змінних у
`docker-compose.yml` — **і інтерполює значення всередині самого файлу**.

**Проблема.** argon2-хеш має вигляд `$argon2id$v=19$m=65536,p=4,t=3$…`. Compose читає `$argon2id`,
`$v`, `$m` як посилання на змінні, підставляє порожні рядки і віддає контейнеру понівечений
`ADMIN_PASSWORD_HASH`. Симптом підступний: контейнер стартує нормально, але жоден пароль не
підходить, а в консолі — стіна `warning: The "argon2id" variable is not set`.

**Рішення.** Два кроки:

1. Конфіг застосунку названо `app.env` — Compose не автозавантажує його.
2. У `docker-compose.yml` вказано `env_file: [{ path: app.env, format: raw }]`, що вимикає
   інтерполяцію і для цього шляху теж.

`apps/server/src/config.ts` шукає `app.env` угору по дереву, тож локальний запуск і контейнер
читають один і той самий файл.

**Перевірено.** `docker compose exec app printenv ADMIN_PASSWORD_HASH` повертає хеш незміненим;
логін у контейнері проходить.

**Наслідок.** Назва нетипова, тож причина зафіксована тут і в шапці `app.env.example` — інакше
хтось «виправить» це назад на `.env` і поверне баг.
