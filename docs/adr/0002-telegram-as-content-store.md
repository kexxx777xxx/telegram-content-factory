# ADR 0002 — Після публікації лишається лише лінк

- **Дата:** 2026-08-02
- **Статус:** прийнято

## Контекст

Опублікований пост уже існує в Telegram: текст, зображення, дата. Тримати другу копію в себе —
це дублювання даних, які й так є, помножене на десятки каналів і роки роботи.

## Рішення

Локально живе **тільки те, що ще не опубліковано**.

Життєвий цикл:

```
planned → generating → ready ─(approval?)─→ publishing → published
          ├─ text_html    у БД              ├─ text_html    → NULL
          ├─ svg_source   у БД              ├─ svg_source   → NULL
          └─ image_path   на диску          ├─ файл         → видалено
                                            └─ permalink    ← записано
```

Після публікації рядок `posts` тримає: дати, `topic_id` + `topic_title`, `tg_message_id`,
`permalink`, `image_kind` і компактний `generation` (модель, `prompt_id@version`, токени, спроби).
Сотні байт.

`permalink` будується при публікації:

- публічний канал → `https://t.me/{username}/{message_id}`
- приватний `-100XXXXXXXXXX` → `https://t.me/c/{XXXXXXXXXX}/{message_id}`

Зображення ніколи не потрапляють у БД. Файл лежить у `data/media` лише поки пост у буфері, і
видаляється одразу після успішної відправки.

## Наслідки

**Позитивні**

- БД лишається малою і швидкою незалежно від віку системи й кількості каналів.
- Бекап дешевий: конфіг і метадані, без бінарників.
- Немає розсинхрону між «нашою» копією поста і тим, що реально в каналі.

**Ціна — і вона реальна**

Bot API **не має методу «прочитати повідомлення за ID»**. `forwardMessage` і `copyMessage`
копіюють вміст в інший чат, але не повертають його в застосунок. Тобто після обнулення
`text_html` текст поста доступний лише за лінком очима, а не програмно.

Закрито: пошук по архіву власних постів, перевикористання старих текстів, аналіз стилю по історії.

Вимикач лишили: `POST_TEXT_RETENTION_DAYS` (дефолт `0` = стирати одразу). Зображення це не
повертає — вони не зберігаються за жодного значення.

## Що це прибрало з попереднього дизайну

Розглядався варіант із vault-чатом: заливати картинку в приватний чат, зберігати `file_id` і
публікувати без повторного аплоаду. Відкинуто як зайву механіку — `file_id` дійсний лише для
бота, що його завантажив, тож це вимагало б додаткових ботів у додаткових чатах. Звичайний
аплоад файлу зі staging простіший і достатній.
