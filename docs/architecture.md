# Архітектура

## Що це

Мультипроєктна система, яка веде кілька Telegram-каналів одночасно. Для кожного каналу
(«проєкту») тримає власний банк тем, власний голос, власний розклад, власні ланцюжки моделей і
власні промпти. Цикл: **тема → текст → зображення → публікація**, усе через AI.

## Компоненти

```
┌─────────────┐     ┌──────────────────────────────────────────┐
│  Web (SPA)  │────▶│ Express API        apps/server/src/api   │
│ React+Vite  │     ├──────────────────────────────────────────┤
└─────────────┘     │ Planner tick  ─┐                         │
                    │ Publisher tick─┼─▶ jobs (Postgres)       │
                    │                │                         │
                    │ Worker pool ◀──┘  SKIP LOCKED            │
                    │   │                                      │
                    │   ├─▶ chain runner ─▶ rate limiter ─▶ Gemini
                    │   ├─▶ SVG engine   ─▶ sanitize ─▶ resvg ─▶ staging
                    │   └─▶ publisher    ─▶ Telegram Bot API
                    └──────────────────────────────────────────┘
                                      │
                              ┌───────┴────────┐
                              │  PostgreSQL    │  метадані + буфер
                              └────────────────┘
```

Один процес: HTTP, планувальник і воркери живуть разом. Лідерство планувальника захищене
`pg_advisory_lock`, тож другий інстанс не подвоїть слоти.

## Три цикли

| Цикл | Період | Що робить | LLM? |
| --- | --- | --- | --- |
| Planner | 60 с | рахує слоти в таймзоні проєкту, створює `posts`, ставить джоби | ні |
| Worker pool | постійно | єдине місце викликів моделей | так |
| Publisher | 30 с | відправляє готове в Telegram, чистить за собою | ні |

Рознесення генерації й публікації в часі — центральне рішення. При `posts_buffer ≥ 1` пост
готується за `lead_time_minutes` до слоту, тож момент публікації не залежить від доступності
моделі. `posts_buffer = 0` вмикає JIT-режим: publisher ставить джобу з високим пріоритетом просто
в слот.

## Життєвий цикл поста

```
planned → generating → ready ─(approval?)─→ publishing → published
          ├─ text_html    у БД              ├─ text_html    → NULL
          ├─ svg_source   у БД              ├─ svg_source   → NULL
          └─ image_path   на диску          ├─ файл         → видалено
                                            └─ permalink    ← записано
```

Після публікації рядок важить сотні байт: дати, тема, `permalink` і компактні метрики генерації.
Див. [ADR 0002](adr/0002-telegram-as-content-store.md).

## Тротлінг

Стан ліміту — рядок у `rate_limit_state` з ключем `(api_key_id, model)`:

- **Token bucket** — немає слота, джоба не спить, а переноситься на час поповнення; воркер вільний.
- **Circuit breaker** — 429 з `retryDelay` пише `blocked_until` для цієї пари; усі воркери
  пропускають її миттєво, не витрачаючи таймаут.
- **Ланцюжок ключів** — ключ проєкту, потім глобальний фолбек із найжорсткішим бюджетом.

Свідомо на ключ, а не на «групу квоти»: див. [ADR 0003](adr/0003-rate-limit-per-key.md).

## Промпти й моделі

Пʼять дій: `topics`, `post_text`, `svg`, `svg_repair`, `image_prompt`. У кожної — упорядкований
ланцюжок кроків (`model_chain_steps.position`).

Промпт для кроку резолвиться так:

```
step.prompt_override  →  project prompt (action)  →  global default prompt (action)
```

Редагування промпта не мутує рядок, а створює нову `version`. Пост записує в `generation`
використані `prompt_id@version` і модель — це єдине, що переживає публікацію, і єдиний спосіб
пояснити просідання якості заднім числом.

## Дедуп тем

Дві лінії, бо жодна поодинці не працює.

**Лексична — тверда гарантія.** `normalizeTopic()` зводить назву до ключа: нижній регістр,
зняття пунктуації, викидання стоп-слів, грубий стемер для кирилиці, сортування токенів.
Сортування робить ключ незалежним від порядку слів, стемер — від відмінка:

```
"Circuit Breaker у мікросервісах"      → breaker-circuit-мікросервіс
"Мікросервіси та Circuit Breaker"      → breaker-circuit-мікросервіс
"Патерн Circuit Breaker мікросервіси"  → breaker-circuit-мікросервіс
```

Стемер навмисно грубий: злити дві різні теми в один ключ коштує пропущеної теми, а не злити
дублікати — коштує повторного поста. Перша помилка дешевша.

Унікальність тримає індекс `topics_project_hash_uniq`, а не перевірка в коді: два паралельні
джоби поповнення інакше обидва пройшли б перевірку в памʼяті.

**Семантична — делегована промпту.** Порівняння рядків не спіймає синоніми й перефразування,
тому наявні назви передаються в промпт, і модель просять їх уникати. Це чесна межа: код не
претендує на розуміння змісту.

## Схема БД

10 таблиць, `apps/server/src/db/schema.ts`:

| Таблиця | Роль |
| --- | --- |
| `projects` | канал + голос + розклад + режими |
| `api_keys` | ключі провайдерів, шифровані; scope global або project |
| `prompts` | версіоновані промпти в трьох скоупах |
| `model_chains` / `model_chain_steps` | ланцюжки моделей на дію |
| `topics` | банк тем, дедуп за `normalized_hash` |
| `posts` | слот + вміст (поки в буфері) + permalink (після публікації) |
| `jobs` | черга з `dedupe_key` та `SKIP LOCKED` |
| `rate_limit_state` | bucket + breaker на `(ключ, модель)` |
| `events` | аудит із ретеншном |

Індекси, що несуть гарантії:

- `jobs_dedupe_uniq` — партіальний унікальний на `pending|running`: ідемпотентність постановки
  джоб, при цьому той самий ключ можна перевикористати після завершення.
- `posts_slot_uniq` на `(project_id, scheduled_at)` — подвійний тік планувальника не створить
  два пости на один слот.
- `topics_project_hash_uniq` — дедуп тем у межах проєкту.
- `jobs_claim_idx` партіальний на `pending` — claim не сканує історію.

## Черга й планувальник

**Claim** — `FOR UPDATE SKIP LOCKED` в одному стейтменті з підзапитом: вікна, у якому два воркери
побачили б той самий рядок, не існує. Перевірено на 6 воркерах і 3 джобах — нуль подвійних видач.

**Ідемпотентність** — `dedupeKey` + партіальний унікальний індекс на `pending|running`. Той самий
ключ можна перевикористати після завершення, що й потрібно для повторюваних слотів.

**Три способи завершити джобу:**

| Результат | Що робить | Спроба витрачається? |
| --- | --- | --- |
| `done` | завершено | — |
| `RescheduleJob` | `pending` з новим `run_after` | **ні** |
| помилка | backoff або `dead` після `max_attempts` | так |

Розділення `RescheduleJob` і помилки — принципове. Вичерпана квота повертає момент, коли
запобіжник відкриється; якби це рахувалось спробою, джоба гарантовано померла б, не дочекавшись
відновлення квоти. Backoff рахується в SQL від `attempts` самого рядка — інакше «експонента» була б
декоративною і кожен ретрай чекав би однаково.

**Reaper** повертає джоби, що застрягли в `running` після смерті воркера: без нього їхні
`dedupe_key` назавжди блокували б нову роботу.

**Планувальник** тікає раз на хвилину під `pg_try_advisory_xact_lock`. Другий інстанс просто
пропускає тік. `posts_slot_uniq` — друга лінія: навіть без лока слот не стане двома постами.

Генерація стартує за `lead_time_minutes` до слоту **плюс стабільний зсув на проєкт**, похідний від
його id. Випадковий зсув ламав би ідемпотентність (кожен тік давав би інший `run_after`), а без
зсуву десятки проєктів зі слотом 09:00 стріляли б у модель в одну секунду.

## Двигун зображень

Дві гілки, вибір на проєкт через `image_mode`.

**SVG** — `модель → санітайзер → ремонт → наступна модель → детермінований fallback`.

Санітайзер робить дві різні роботи, і обидві свідомо в коді, а не в промпті:

1. *Безпека.* Результат рендериться на сервері **і** показується inline в адмінці, яка тримає
   бот-токени. `<script>` або зовнішній `href` виконались би саме там.
2. *Стиль.* Правило «жодного тексту всередині» і фіксований 16:9 — продуктові вимоги. Модель
   дотримується їх здебільшого, а «здебільшого» — це не правило.

Кутові випадки, знайдені тестами: перевірка DOCTYPE має йти **до** зрізання обгортки (інакше
зрізання ховає XXE), а `parse()` у fast-xml-parser не доводить коректність — потрібен `XMLValidator`.

**Fallback** малюється кодом і не може впасти — у цьому його сенс. Слот без зображення змінив би
формат каналу, а пропуск слоту втратив би публікацію через проблему рендеру.

**Image-модель** — `image_prompt` (текстова модель пише промпт) → `image` (модель малює).
Fallback тут навмисно відсутній: ескіз олівцем не пасував би проєкту, що обрав фотографічну
ілюстрацію, тож помилка лишається помилкою.

### Заміряна деталь про порядок моделей

Дефолтний ланцюжок для SVG починається з **lite**-моделі, і це вимір, а не вподобання: схема — це
близько 4000 вихідних токенів, чого старші моделі не встигають за 60 с, тоді як lite повертає
результат приблизно за 11. Зі звичайним порядком кожна ілюстрація спершу спалювала повний таймаут.
Тому ж SVG-дії дано бюджет у 120 с замість прозового.

## Публікація

Publisher tick (30 с) сам нічого не відправляє — він лише **ставить джоби**, тож публікація
успадковує ретраї й перенесення черги замість того, щоб дублювати їх на таймері.

| Стан поста в момент слоту | Дія |
| --- | --- |
| `ready` | `publish_post` з пріоритетом 20 |
| `planned` (JIT або генерація відстала) | `generate_and_publish` з пріоритетом 30 |
| прострочено понад grace, `miss_policy=skip` | `skipped` із причиною |
| прострочено понад grace, `publish_late` | далі чекає |

`generate_and_publish` — **одна** джоба, а не дві зчеплені: інакше слот міг би отримати свіжий
пост, який ніхто не публікує.

**Ліміт підпису** — найнезручніше місце. Telegram дозволяє 1024 символи на фото і 4096 у
повідомленні, а пости регулярно потрапляють між. Замість обрізати авторський текст довгий пост
іде як фото + повідомлення, а permalink вказує на фото. Розбиття — по межах абзаців: посимвольне
дало б незакритий тег, а Telegram відхиляє незбалансований HTML.

**Очистка — частина публікації, не наслідок.** У тій самій транзакції: текст і `svg_source` в
`NULL`, тема в `used`, записаний `permalink`, подія в аудит. Файл видаляється **після** коміту —
видалений раніше, він залишив би пост, який уже не опублікувати.

`retry_after` від Telegram перетворюється на перенесення джоби без витрати спроби; 401 навпаки
термінальний — невірний токен не почне працювати з четвертої спроби.

## Адмін-бот (опційний)

`ADMIN_BOT_TOKEN` порожній — бот вимкнено, і система працює повністю. Єдине, що без нього
недоступне, — режим `publish_mode: approval`; проєкт на `auto` не помічає його відсутності.

**Розділення ботів.** Читає апдейти лише адмін-бот, і лише `callback_query`. Паблішер-боти
пишуть і не мають циклу оновлень: інакше polling множився б на кількість проєктів без жодної
користі.

**Авторизація** — whitelist `ADMIN_USER_IDS`. Це єдиний бар'єр: без нього будь-хто, хто знайшов
бота, натискав би кнопки.

**Алерти** записуються в `events` **завжди**, незалежно від того, чи налаштований бот — аудит
є довговічним записом, Telegram лише канал доставки. Доставка при цьому дедуплікується на 10
хвилин: без цього збій квоти на пʼятдесяти проєктах надіслав би пʼятдесят однакових повідомлень
за хвилину й привчив оператора вимкнути сповіщення.

**Бекап** — JSON-знімок конфігурації, gzip, раз на добу в адмін-чат. Свідомо не `pg_dump`: той
додав би клієнтський бінарник в образ і звʼязав його з версією сервера заради бази, що тримає
конфіг і метадані, а не контент. `pg_dump` лишається задокументованим шляхом відновлення в
runbook. Секрети експортуються **зашифрованими**, тож без `APP_ENCRYPTION_KEY` файл марний —
саме та властивість, якої треба від файлу, що йде через чат.

## Зберігання

- **Postgres** — конфіг, метадані, черга і вміст постів, що ще в буфері.
- **`data/media`** — staging-файли зображень буферних постів. Обмежений зверху
  `проєкти × posts_buffer × ~300 КБ`. Не бекапиться: вміст відновлюється перегенерацією.
- **Telegram** — архів опублікованого.

## Безпека

- Бот-токени й API-ключі — AES-256-GCM (`APP_ENCRYPTION_KEY`), назовні лише маска.
- Auth адмінки перемикається `ADMIN_AUTH_ENABLED`; вимкнення завжди гучне — warn у лог і
  постійний банер в UI. `ADMIN_BIND_HOST` за замовчуванням `127.0.0.1`.
- SVG від моделі санітизується детерміновано перед рендером і перед показом в UI.
